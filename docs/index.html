A from-scratch LLM inference engine in Python + NumPy

Study & learning project — not a performance project
The goal is to understand how an LLM inference engine works from the inside by building one from scratch. The code prioritizes clarity and correctness over speed — not production use or benchmark chasing. Created with the assistance of Qwen4.0 Max Preview and Opencode.

naive-inference runs Qwen3.8-27B — a 2026 hybrid-attention model — in Python + NumPy, with optional CUDA via CuPy. The engine is written once against a NumPy-compatible namespace (arrays.xp), so the same code path scales from a simple PC to a DGX Spark. Every piece was built from scratch for learning: the safetensors loader, the BPE tokenizer, both attention mechanisms, sampling, a chat CLI, and an OpenAI-compatible server. Correctness was proven layer-by-layer against Hugging Face.

Overview — the hybrid architecture

Qwen3.8-27B (model_type: qwen3_5) is hybrid: most layers replace softmax attention with a recurrent linear-attention mechanism whose memory is a fixed-size matrix. Every 4th layer keeps classic full attention. Development happens against Qwen3.5-4B (same architecture, smaller dimensions); running the 27B model is a matter of pointing at a different weights directory.

token ids→ embedding→ [linear ×3 → full] ×16→ RMSNorm→ lm_head→ logits [248320]→ sample → next token

The payoff: long context is cheap. Full-attention layers need a KV cache that grows with the sequence; linear-attention layers need only a constant ~3 MB state each. Try it yourself in the memory calculator.

Hardware adaptation — simple PC to DGX Spark

The engine adapts to the available memory and compute automatically: only the backend (NumPy vs CuPy) and the weight dtype (fp32 vs bf16) change, chosen from a memory budget at load (Model.load(device="auto", weight_dtype="auto")).

  • fp32 weights when they fit — each matrix is converted from bf16 once at load; matmul reads fp32 directly (BLAS on CPU, cuBLAS on CUDA). The fast path.
  • bf16 weights otherwise — matrices stay uint16 and are converted inside each matmul. Half the memory. On CPU they are zero-copy mmap views: a 55 GB checkpoint loads in ~0.2 s and only touched pages consume RAM — this is what lets a 62 GB host run the 27B model at all.
  • CPU — NumPy matmul uses multithreaded BLAS; tune with OPENBLAS_NUM_THREADS / OMP_NUM_THREADS.
  • DGX Spark (GB10, ARM, CUDA 13, 128 GB unified memory) — the 27B model fits in fp32 (~108 GB) in unified memory: weights converted once, matmul on cuBLAS, no per-call conversion and no disk page faults. Install cupy-cuda13x[ctk]; the engine code is unchanged.
  • Small GPU (e.g. RTX 4060 8 GB) — 4B bf16 (~9.3 GB) exceeds VRAM, so auto falls back to CPU. CUDA is still exercised via synthetic models and layer-level parity tests.

Layout

naive_infer/            ENGINE (pure NumPy/CuPy + regex; never imports torch)
  arrays.py             backend selection (numpy/cupy), bf16<->fp32, device moves
  safetensors.py        header parse, mmap, zero-copy uint16 views, shards
  config.py             config.json parsing + validation, derived dimensions
  weights.py            tensor resolution, memory-aware placement, linear()
  ops.py                RMSNorm (2 variants), SiLU, softmax, RoPE, L2norm, ...
  state.py              KVCache, ConvState, SSMState, SeqState
  forward.py            full attention, Gated DeltaNet, MLP, whole forward
  model.py              Model: load, embed, forward, generate/generate_stream
  sampling.py           greedy, temperature, top-k, top-p
  tokenizer/            NFC, regex pretokenizer, byte-level BPE, ChatML template
  server.py             OpenAI-compatible HTTP API (stdlib http.server, SSE)
  cli.py                inspect, tokenize, embeddump, generate, chat, serve
oracle/                 ORACLE — separate deps (torch/transformers/tokenizers)
  m0_dump.py ... m5_dump.py   ground-truth dumps (.npy) and goldens
  dumps/                oracle output (git-ignored; regenerate via oracle/ scripts)
  requirements.txt      oracle-only dependencies (full); requirements-base.txt (M0/M4)
tests/                  pytest: unit + oracle comparison + CPU/GPU parity
  golden/               tokenizer/chat goldens (generated by the oracle; tracked)
docs/                   SPEC.md, IMPLEMENTATION.md, HARDWARE.md + HTML site

Engine/oracle separation is enforced: tests/test_no_oracle_deps.py fails if any naive_infer/ module imports torch/transformers/tokenizers.

Build, test, usage

# Python 3.10+ and uv; the engine needs only NumPy + regex (CUDA optional)
uv venv                                    # creates .venv
uv pip install -r requirements.txt -e .    # CPU engine + pytest + CLI
# optional CUDA (pick ONE matching your platform):
uv pip install -r requirements-cuda12.txt  # x86 + CUDA 12 driver (e.g. RTX 4060)
uv pip install -r requirements-cuda13.txt  # DGX Spark (ARM + CUDA 13)

source .venv/bin/activate
pytest                             # unit + oracle tests (skip if weights absent)
./download-models Qwen3.5-4B        # fetch into ./models (default NAIVE_INFER_MODELS root)

# Model summary (-tensors lists weights, -embed ID inspects a row)
naive-infer inspect -model Qwen3.5-4B

# Encode text (-pieces shows raw byte-level pieces) / decode ids
naive-infer tokenize -model Qwen3.5-4B -text "Olá, mundo!" -pieces

# Continue text (greedy by default; -temp/-top-k/-top-p enable sampling)
naive-infer generate -model Qwen3.5-4B -text "Once upon a time" -max-new 32

# Interactive chat (ChatML, streaming; /exit and /reset)
naive-infer chat -model Qwen3.5-4B -system "You are helpful." -no-think

# OpenAI-compatible API server (SSE streaming, reasoning_content split)
naive-infer serve -model Qwen3.5-4B -addr 127.0.0.1:8080

-device {auto,cpu,cuda} and -weight-dtype {auto,bf16,fp32} control placement. Models live in ./models/<NAME> (the default NAIVE_INFER_MODELS root); fetch them with ./download-models Qwen3.5-4B (or Qwen3.8-27B; --config-only for tokenizer-only). Weights: ~9.3 GB bf16 for 4B, ~55.6 GB for 27B. See the README for details and the oracle section for the verification workflow.
